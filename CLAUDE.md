# K-Hub — Contesto Progetto

## Cos'è
K-Hub è una piattaforma web per aggregare eventi di rental karting in Italia e (in roadmap) tracciare le statistiche dei piloti a livello nazionale. Target: piloti rental, in particolare neofiti.

## Stack reale (NON Flutter — attenzione, vecchi prompt lo presumevano)
- **Frontend**: React 19 + Vite, react-router-dom v7, lucide-react per le icone, Framer Motion solo per l'animazione d'entrata tra le route (`App.jsx`). Stile **Manifesto** (design system K-Hub: locandine anni '50-'60, Archivo largo corsivo + Doto per tempi e contatori, giallo-corsa/rosso-corsa/blu-inchiostro su carta): tutto in `frontend/src/styles/manifesto.css` sotto `.kh-theme` (token + componenti `kh-*`), base globale (reset/body) in `frontend/src/index.css`, componenti in `frontend/src/components/kh/`. Una sola shell (`SiteHeader`/`SiteFooter`) per tutte le route, con pagina 404 (`NotFound.jsx`). Niente Tailwind (rimosso: non era mai importato). Il vecchio look (tema dark "Rally Game Menu", HUD, lime) è stato rimosso.
- **Backend**: Supabase (PostgreSQL + Auth), RLS attiva. Schema base in `database_schema.sql`, esteso dalle migration in `migrations/` (001→004, applicate al DB live a mano via SQL editor: il CLI Supabase non ha access token su questa macchina — mai tentare scritture di test sul DB di produzione).
- **Scraper**: Python, 4 fonti HTTP orchestrate da `run_all.py`: WeRace (`werace_scraper.py`) e RKC ASI (`rkc_asi_scraper.py`) via API JSON pubblica del plugin WordPress "The Events Calendar" (`wp-json/tribe/events/v1/events`: data, pista, indirizzo, costo reali), XRace (`products.json` Shopify, data dal titolo con anno dedotto da `published_at`; i prodotti senza data, es. campionati, sono saltati), KRM (BeautifulSoup). SWS (`scrape_sws_events` in `scraper_base.py`, Playwright + stealth) NON è in `run_all.py`: il sito è dietro reCAPTCHA, non si automatizza. WeRace e le tappe rkc già coprono gran parte delle gare SWS. Le sessioni di prova libera WeRace (Free Track/Free Practice) sono escluse dal calendario. Scrive nella tabella `events` con upsert dedup su `(source_url, event_date)` e arricchisce region/format a scrape-time. Usa la libreria interna `it-scraper-toolkit` (repo locale `C:\Users\FCD\Documents\it-scraper-toolkit`, GitHub privato `Fuchs665/it-scraper-toolkit`, installata editable via requirements.txt): `configure_stdio()` in `scraper_base` rende le print encoding-safe su Windows (niente più crash da emoji/accenti), `HttpClient` con retry/backoff + rate limit 1 req/s + user-agent onesto "K-Hub-Scraper/0.1" per le 4 fonti HTTP (verificato: nessun sito lo blocca), `parse_italian_date` per le date SWS/KRM. `run_all.py --dry-run` esegue tutto senza scrivere sul DB, segnala i duplicati cross-fonte (report-only) e le righe del DB ormai obsolete (con la sola anon key in env è una lettura). Un run reale, dopo l'upsert, rimuove le righe obsolete create dallo scraper (`created_by` nullo): stessa `source_url` con data diversa (gara spostata) o gara futura sparita dalla fonte; max 25 rimozioni per run, oltre serve `--force-prune`; KRM (URL condiviso) e le fonti non raggiunte nel run sono escluse.
- **Deploy/vincoli**: solo free tier Supabase e Vercel. Nessuna spesa.

## Problemi noti / debito tecnico
1. **RLS lasca su risultati**: le policy su `race_results`/`lap_times` sono `FOR ALL TO authenticated WITH CHECK (true)` — qualsiasi utente loggato può inserire/modificare risultati altrui. Accettato per l'MVP; in futuro serve un ruolo organizer.
2. **Scraper**: rimesso a regime a ottobre 2026 (WeRace via API con date vere, XRace con anno corretto, riconciliazione righe obsolete). Un run reale richiede `SUPABASE_SERVICE_ROLE_KEY` in `scraper/.env.local` (oggi vuota, manca la chiave). Resta da automatizzare il run periodico (le 4 fonti HTTP girano anche in CI; SWS no).
3. **Nessuna UI di modifica/cancellazione risultati**: OrganizerDashboard permette solo l'inserimento; errori di battitura si correggono solo dal DB.
4. **Artefatti di debug tracciati in git**: `scraper/sws_races.html` + `sws_races_files/`, `debug_screenshot.png` — da pulire dopo aver verificato che l'HTML non serva come fixture.
5. **Possibile duplicazione cross-fonte per le tappe RKC ASI**: alcune tappe condividono la pista con eventi già scrapeati da altre fonti (es. Misanino KCE, già noto a KRM) ma con `source_url` diverso — la dedup upsert è su `(source_url, event_date)`, quindi non rileva duplicati tra fonti diverse per lo stesso giorno/pista. `run_all.py` ora li segnala automaticamente a ogni run (report-only via `toolkit.dedupe.find_duplicates` su data+pista, filtrato su domini sorgente diversi); al run del 2026-07-20 nessun duplicato cross-fonte in pratica. Se in futuro il report ne trova, decidere quale fonte vince prima di automatizzare la rimozione.

## Convenzioni
- Lavorare in iterazioni: proporre → conferma → implementare.
- Query sui tempi/classifiche ottimizzate lato DB (viste o RPC Postgres), non aggregazioni in JS sul client.
- Gestire sempre dati incompleti (circuiti che non forniscono tutti i tempi).
- UI: look sportivo/tecnico, numeri leggibili, tabelle responsive anche su schermi stretti.
- Commit piccoli e descrittivi.
